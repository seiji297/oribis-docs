## 1. エグゼクティブサマリー

**Oribis** = MCP Server型AIエージェント開発プラットフォーム（デスクトップネイティブ）。

- **MCP Server**: 外部AIクライアント（Claude Code, Codex CLI等）がMCP経由で接続。LLM知能はクライアント側が提供
- AI人格エンジン（Anima）による自律的キャラクター
- エンジン非依存のAIデバッグシステム（AppBridge）
- 3Dアバター統合（VRM/FBX/MMD）+ TTS + 感情表現 + リップシンク
- DAGワークフロー実行エンジン
- プラグインSDKによる拡張

**アーキテクチャ前提**: Oribis = MCP Server。LLMはユーザーの外部MCP Client（Claude Code, Codex CLI等）が提供。Oribis自体にLLMは内蔵しない。

**ビジネスモデル**: 全コードFSL v1.1公開 + ビルド済みバイナリ有料（BOOTH ¥980 / $6.99）

**ポジショニング**: 「キャラクターAI」ではなく「MCP対応AIエージェント開発プラットフォーム」

## 2. プロダクトポジショニング

### なぜ「AIエージェント開発プラットフォーム」か

Character.ai/Convai等の「キャラクターAIサービス」は:
- クラウド専用（ローカルLLM不可）
- 閉鎖的API（開発者拡張不可）
- チャット特化（ツール統合なし）

Oribisの差別化:
- **MCPプロトコル統合**: LLMエージェントから直接操作。Claude/GPT/Geminiどれでも
- **デスクトップネイティブ（Tauri）**: ローカルLLM対応。データ主権
- **DAGワークフロー実行**: 複数AIステップをグラフで定義・実行
- **AIデバッグ**: 任意外部アプリ（ゲーム、CLIツール等）をAI駆動テスト
- **プラグインSDK**: 開発者エコシステム

### ターゲットセグメント

| セグメント | ニーズ | Oribisの価値 | 優先度 |
|-----------|-------|-------------|--------|
| AIエージェント開発者 | ワークフロー実行・デバッグ・MCP統合 | Orchestrator + AI Debug | P0（初期） |
| ゲーム開発者（インディー） | NPC AI + テスト自動化 | Anima + AppBridge | P1（中期） |
| VTuber/配信者 | 自律的AIキャラクター | Anima + 3Dアバター | P1（中期） |
| 開発スタジオ | Enterprise統合・カスタム人格 | 全機能 + サポート | P2（長期） |

## 3. ライセンス・収益モデル

### v4.1方針: FSL v1.1ソース公開 + ビルド済みバイナリ販売

```
┌─────────────────────────────────────┐
│  oribis (公開リポジトリ)             │
│  FSL v1.1 — ソース公開・全機能閲覧可 │
│                                      │
│  ・MCP Server/Broker                 │
│  ・Anima全体（長期記憶+好感度含む）   │
│  ・AppBridge + AI Debug全体          │
│  ・DAG実行 + ノードエディタUI        │
│  ・3Dアバター + TTS + 感情表現       │
│  ・Plugin SDK + Web Remote           │
│  ・ナレーション生成                   │
│                                      │
│  許可: 個人利用・社内利用・学習・研究  │
│  禁止: 商用競合・フォーク再配布       │
│  → 2028-05-03に自動Apache 2.0化      │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│  BOOTH / GitHub Releases             │
│  ビルド済みバイナリ                   │
│  ¥980（EA）/ $6.99                   │
│                                      │
│  → コンパイル不要。ダウンロード即使用  │
│  → Tauri(Rust)ビルドは一般人には困難  │
└─────────────────────────────────────┘
```

### なぜこの方式か

1. **Pro分離コスト0**: コード分離不要。今すぐ公開できる
2. **ソース公開で信頼構築**: コード全公開 → ユーザーが中身を確認できる安心感
3. **FSLで競合防壁**: フォーク+再配布禁止 → 中国企業のパクリ対策
4. **社内利用OK**: 企業の内部利用は許可 → 採用障壁を下げる
5. **自然な有料化**: Rustビルド環境構築は非開発者にはハードル高い → ビルド済み = 価値
6. **後からPro分離可能**: ユーザーが付いてから機能分離しても遅くない
7. **2年後Apache 2.0化**: Change Date後に完全OSSとなりコミュニティ拡大

### リスク

- 開発者はソースからビルドできる → 有料購入しない可能性（個人利用は許可のため）
- FSL v1.1の法的拘束力 → OSSコミュニティからの批判の可能性
- ビルド済みバイナリだけでは収益が極めて限定的

**→ これらは全て「ユーザーが付いてから」の問題。今は気にしない。**

## 付録A: v3→v4 変更理由

v3（Pro分離3本柱）からv4（FSL v1.1ソース公開+ビルド販売）に変更した理由:

1. **ユーザー0人**: Pro分離に13-16日かけても、買う人がいなければ意味なし
2. **長期記憶分離が困難**: lib.rs 50+箇所のAnima依存解消に5-7日。最もコスト高い作業
3. **PMF未検証**: 何がProの価値かはユーザーの反応を見ないとわからない
4. **公開速度優先**: Pro分離13-16日 → ビルド販売準備5-6日。8-10日の短縮
5. **後からPro化可能**: ユーザーが付いてから「この機能はPro化すべき」が見えてくる

### 将来のPro分離候補（PMF検証後に検討）

| 機能 | 分離難度 | 分離日数 |
|------|---------|---------|
| ノードエディタUI | 低 | 0.5-1日 |
| AI Debugセッション管理 | 低〜中 | 1.5-2日 |
| Narration | 低 | 0.5-1日 |
| Scheduler | 低 | 0.5日 |
| 長期記憶+好感度 | **高** | 5-7日 |

## 付録B: Codex Adviser OSS/Pro分離レビュー（2026-05-20）

v3時点でCodex Adviser（gpt-5.5）に分離設計をレビュー依頼した結果の要約。v4では即座に適用しないが、将来のPro分離時に参照する。

### 主要指摘

1. **物理分離推奨**: feature gateだけではソース公開分離にならない。最終形はprivate crate/package
2. **AnimaProvider trait分割**: 1つの神traitにせず、ConversationProvider/EmotionProvider/MemoryWriter等に分離
3. **TypeScript**: VITE_PRO env分岐ではなくnpm workspace + FeatureRegistry方式
4. **debug_session**: 型はOSS、実装はPro
5. **テスト3層**: OSS単体 / OSS default / Pro統合
6. **CI 2系統**: OSS単独CI + Pro統合CI
7. **段階的移行**: 境界作り → stub実装 → 柱ごとに移動
8. **見落としリスク**: git historyにProコード残留、DBスキーマ漏洩、空リンク

**フル回答**: `/tmp/adviser-result.md`（セッション内参照用）
